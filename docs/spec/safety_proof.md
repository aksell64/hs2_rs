# Лемма (safety-ядро)

## Обозначения

- `X ⪯ Y` — X является предком-или-равен Y (Y расширяет X). Конфликт: `X ⋠ Y ∧ Y ⋠ X`.
- Для сертифицированного блока пишем его ранг как view его QC: `rank(B) = V(QC(B))`.
- `qc_lock(r)`, `votedView(r)` — состояние реплики r.
- n = 3f+1, кворум = n − f = 2f+1.

## Формулировка

Пусть честная реплика закоммитила блок B **directly** во view v. По правилу коммита
это значит: существуют два сертификата на соседних views
```
QC(B) во view v   и   QC(B_c) во view v+1,   где B_c = child(B) (B_c.parent = B).
```
Тогда для любого сертифицированного блока B' с `V(QC(B')) ≥ v` выполнено `B ⪯ B'`
(B' равен или расширяет B).

Замечание. Формулировка — про **direct** commit (есть двойной сертификат на соседних
views). Любой indirect-коммит подтягивается как предок какого-то direct-коммита
(`onCommit` рекурсивно исполняет предков), поэтому итоговая теорема safety выводится
из этой леммы отдельным шагом (см. конец).

## Построение множества P (несущий шаг, был пропущен)

P нельзя постулировать — его надо предъявить и доказать три его свойства.

Определение:
```
P := множество реплик, проголосовавших за B_c во view v+1.
```

(1) **|P| ≥ 2f+1.** QC(B_c) во view v+1 существует (посылка о direct commit), а QC
требует 2f+1 голосов. Значит голосовавших за B_c — не меньше 2f+1.

(2) **Честных в P ≥ f+1.** Из 2f+1 голосовавших не более f византийских.

(3) **Каждый честный p ∈ P залочен на ⪰ B рангом ≥ v** — в момент своего голоса за B_c.
Это НЕ следствие «цепочка прямая», а следствие правила лока и порядка вызовов в
`onReceiveProposal`:
- предложение B_c несёт `B_c.justify = QC(B)` (честный лидер строит B_c поверх B);
- `onReceiveQC(B_c.justify)` вызывается ПЕРВЫМ, до проверки голосования;
- в `onReceiveQC`: `if QC(B).viewNumber (=v) > qc_lock(p).viewNumber then qc_lock(p) ← QC(B)`.

Чтобы p проголосовал за B_c, должна пройти проверка
`B_c.justify.viewNumber ≥ qc_lock(p).viewNumber`, то есть `v ≥ qc_lock(p).viewNumber`.
В связке с тем, что onReceiveQC уже отработал:
- либо `qc_lock(p)` был ниже v и поднялся ровно на QC(B) → `qc_lock(p).node = B`, ранг v;
- либо `qc_lock(p)` уже был ранга ≥ v; но тогда проверка `v ≥ qc_lock(p).viewNumber`
  проходит только при равенстве, а по per-view uniqueness (см. базу) QC ранга v
  единствен и это QC(B) → снова `qc_lock(p).node ⪰ B`.

Итог: в момент голоса за B_c каждый честный p ∈ P имеет `B ⪯ qc_lock(p).node` и
`qc_lock(p).viewNumber ≥ v`.

> Где здесь фикс #1: свойство (3) держится только потому, что есть QC(B_c) на
> **соседнем** view v+1. Без соседнего сертификата P — это «голосовавшие за что-то»,
> без гарантии, что 2f+1 залочены на B рангом ≥ v. Соседние views в правиле коммита —
> это ровно то, что рождает P с нужным свойством.

## Инвариант монотонности лока (нужен, чтобы «дожить» до v')

Лемма-помощник. Для честной r: `qc_lock(r).viewNumber` не убывает во времени, и
`qc_lock(r)` в любой момент равен некоторому реально сформированному QC.

Доказательство. Единственное присваивание — `qc_lock ← qc` под гардом
`qc.viewNumber > qc_lock.viewNumber` в `onReceiveQC`, и qc туда попадает только после
`verifyQC(qc)`. Значит ранг только растёт, а node — всегда узел валидного QC. ∎

Следствие: если честная r залочена на ⪰ B рангом ≥ v в момент t, то в любой
момент t' > t её `qc_lock(r).viewNumber ≥ v`, а `qc_lock(r).node` — узел QC ранга ≥ v.
Останется показать, что этот узел всё ещё ⪰ B — это и даст индукция.

## Доказательство леммы (индукция по рангу v')

Индукция по `v' = V(QC(B'))`, для всех v' ≥ v.

### База: v' = v

В одном view сертификат существует не более чем за один блок: QC требует 2f+1 голосов,
а каждая честная реплика голосует во view не более раза (`votedView < curView` ⟹
`votedView ← curView`), и два кворума пересекаются по честной. Значит QC(B') во view v —
это QC(B), то есть B' = B, и `B ⪯ B'`. ∎(база)

### Шаг: пусть лемма верна для всех рангов из [v, v']; докажем для v'+1

Гипотеза индукции (IH): любой сертифицированный блок ранга в [v, v'] расширяет B.

Возьмём произвольный сертифицированный блок ранга v'+1; пусть его предложил лидер как
B*. Предположим противное: `B ⋠ B*` (B* конфликтует с B или лежит вне ветки B).
Покажем, что тогда QC(B*) во view v+1'... — точнее, что QC(B*) ранга v'+1 не может
существовать.

**Шаг A. Куда указывают локи честных из P к моменту голосования за B*.**
Возьмём честного p ∈ P (их ≥ f+1). К моменту, когда до p доходит B*, значение
`qc_lock(p)` — это QC некоторого ранга k (по инварианту монотонности, k ≥ v, и k ≤ v'
т.к. QC ранга v'+1 ещё не сформирован в момент голосования за первый такой блок).
По IH блок ранга k ∈ [v, v'] расширяет B, значит `B ⪯ qc_lock(p).node`.
То есть **каждый честный p ∈ P залочен на ⪰ B** в этот момент.

**Шаг B. Честный из P не голосует за B*.**
Пусть, от противного, честный p ∈ P голосует за B*. По коду голос требует:
1. `B*.justify.viewNumber ≥ qc_lock(p).viewNumber ≥ v`  (rank-проверка);
2. `B*.justify.node ⪯ B*`  (ancestry-проверка).

Из (1): `B*.justify.viewNumber ≥ v`, и это ранг < v'+1 (justify предложения строго
ниже ранга самого предложения). Значит `B*.justify.node` — сертифицированный блок
ранга в [v, v']. По IH `B ⪯ B*.justify.node`.
Из (2): `B*.justify.node ⪯ B*`. Композиция: `B ⪯ B*.justify.node ⪯ B*`, то есть
`B ⪯ B*`. Противоречие с `B ⋠ B*`.
Следовательно честный p ∈ P за B* **не голосует**.

> Где здесь фикс #2 (ancestry): без пункта (2) из «лок p ⪰ B» нельзя вывести «B* ⪰ B» —
> justify мог бы указывать на ветку B, а сам B* строиться вбок. Тогда честный из P
> проголосовал бы за конфликт, и шаг B рушится. Ancestry связывает «на что залочен
> через justify» с «что реально расширяет B*».
>
> Подслучай равенства (почему `≥`, а не строгое `>`, безопасно): если в (1) равенство
> `B*.justify.viewNumber = qc_lock(p).viewNumber`, то два QC этого ранга по per-view
> uniqueness сертифицируют один блок, т.е. `B*.justify.node = qc_lock(p).node ⪰ B` —
> и вывод B ⪯ B* проходит так же. Равенство не открывает дыры.

**Шаг C. Кворум за B* недостижим.**
За B* могут голосовать все реплики, КРОМЕ честных из P (шаг B). Честных в P ≥ f+1,
поэтому потенциальных голосующих за B* не больше
```
(3f+1) − (f+1) = 2f < 2f+1 = кворум.
```
Значит QC(B*) ранга v'+1 сформироваться не может.

Эквивалентная (более короткая) форма шагов B–C через пересечение: если бы QC(B*)
существовал, два кворума — P и QC(B*) — пересеклись бы по честной r
(`|P|+|QC(B*)|−n ≥ (2f+1)+(2f+1)−(3f+1) = f+1 > 0`); эта r одновременно залочена
на ⪰ B (r ∈ P, шаг A) и проголосовала за B* (шаг B показал, что это невозможно) —
противоречие.

**Вывод шага.** Никакой сертифицированный блок ранга v'+1 не конфликтует с B, то есть
любой такой блок расширяет B. Индукция замкнулась. ∎(шаг)

## Теорема (safety)

Если два блока B_l и B'_l закоммичены на одной высоте l (каждый — честной репликой),
то B_l = B'_l.

Доказательство. Каждый коммит подтягивается direct-коммитом-потомком: B_l закоммичен
из-за direct commit блока B_k (`B_l ⪯ B_k`) во view v, B'_l — из-за direct commit B'_{k'}
во view v'. Без ограничения общности v ≤ v'. Применяем лемму к direct-коммиту B_k
(ранг v) и сертифицированному блоку B'_{k'} (ранг v' ≥ v): получаем `B_k ⪯ B'_{k'}`,
то есть они на одной цепи. Их предки на высоте l совпадают: `B_l = B'_l`. ∎

Следствие: `onCommit` исполняет только предков закоммиченного блока, а все
закоммиченные блоки лежат на одной цепи, поэтому исполненные префиксы честных реплик
согласованы.

## Что осталось за рамками (не safety)

- **Liveness** доказывается отдельно и не выводится отсюда: безопасность декуплена от
  pacemaker. Ручной аргумент — через «потолок сертификатов» под синхронией + честный
  лидер (см. обсуждение), либо машинно как `◇(progress)` под fairness.
- Инвариант монотонности лока и per-view uniqueness — кандидаты в inductive invariants
  для Quint: их индуктивность и есть то, что стоит проверить машиной первым делом.
